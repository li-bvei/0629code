## 1. 结论摘要

项目已经具备比较清晰的核心方向：以“案件”为业务主线，客户、公司、家族成员、案件状态、检查清单、时间线、期限提醒和部分申报书作为基础模块。最新提交也解决了客户列表中的家族显示混乱，并加入了期限提醒的隐藏能力。

但当前仍属于“核心模块分别可用、端到端作业链未闭环”的阶段。最大问题不是缺少页面，而是同一份客户信息在受付、客户主档、家族成员、公司职员、案件和会计之间仍会重复录入或断开；同时列表分页、时区和仪表盘统计存在业务准确性风险。

建议暂缓继续扩展更多报表和独立页面，先完成一条可稳定运行的闭环：

> 新规受付 → 既有客户匹配/新建 → 自动生成案件 → 自动套用案件模板 → 分配担当 → 资料收集与清单 → 期限/下一动作 → 申报与结果 → 完了归档 → 会计关联。

## 5. P0/P1/P2 问题清单

### P0：上线/交付前阻断

- 全量测试不绿，尤其是会计导出和余额定义未形成稳定契约。
- 最新受保护页面无法用真实账号完成端到端验证；本次只完成了登录页和空提交校验。登录页空提交能显示用户名/密码错误，但没有统一错误摘要、自动聚焦和恢复帮助。

### P1：会直接影响日常正确性和工作量

1. **时区不一致**：Django 设置为 UTC，而产品业务明显以日本时间运行；本次运行中系统 `localdate()` 比东京日期早一天。期限、受理日、案件编号月份和日终操作可能出现边界日偏差。统一使用 `Asia/Tokyo`，并补齐跨日 23:xx/00:xx 的测试。
2. **仪表盘统计可能不完整**：`DashboardPage.vue` 调用 `listCases()` 后只使用第一页 `results`，而全局默认分页是 20。案件超过 20 条时，阶段统计、最近案件和处理中数量可能与数据库实际不一致。应提供服务端汇总接口。
3. **选择项可能只取第一页**：受付、案件、案件详情、公司详情、税务更新等页面多处直接调用客户/公司/担当者列表并使用 `results`。客户已有 97 条时，工作人员可能无法从普通下拉框选择第 21 条以后的对象。统一改为远程搜索选择器，或提供明确的“搜索后选择”接口。
4. **客户重复创建风险**：新规受付的事务流程可以一次创建客户、家族成员、公司和案件，但提交前没有姓名/生日/电话/证件号候选匹配。相同客户再次受付会增加重复主档，之后又需要人工合并。
5. **案件登记状态存在绕过专用流程的风险**：`CasePayload` 允许 `registration_status`，但 `CaseSerializer` 没有把它设为只读；通用更新可能绕过专用状态变更接口、警告、备注和时间线。应只允许专用 action/service 修改。

### P2：体验、性能和维护成本

- 期限隐藏只有“隐藏”语义，没有原因、恢复、期限或审计说明；“期限切れ…一括非表示”容易让用户误以为已处理，存在漏办风险。
- 案件清单模板重复套用可能重复添加项目；需要“已套用 / 合并 / 替换”的选择和幂等保护。
- 仪表盘、案件列表的 SerializerMethodField 和期限构建逻辑有逐条查询倾向，数据量扩大后会变慢。
- 客户、案件、公司等通用 ViewSet 仍有硬删除路径；对业务记录建议改为归档/停用，删除限权并记录理由。
- 会计中的支出来源、收入来源仍偏自由文本，与客户/公司/案件未形成稳定关联；会计无法自然回到案件利润或客户账务。
- 菜单、路由和文档同时存在“已完成、准备中、占位、暂停”表达，且日文、中文、英文术语混用。对日本内部事务所，建议统一为日文操作词，中文只留在开发文档。
- 前端构建产物约 1.9 MB minified，建议路由级懒加载和拆分会计/报表模块。

## 6. 建议的目标模型：一个客户、一条案件、一套下一动作

成熟的案件管理产品通常把单一案件记录作为“事实来源”，并将联系人、文件、任务、期限、账务和沟通历史连接到该记录；受付表单采集的数据直接进入案件，模板用于减少重复配置。可参考 [Clio 的案件管理](https://www.clio.com/features/case-management/) 和 [在线受付表单](https://www.clio.com/features/online-intake-forms/?cta=lexicata)。多案件、多活动、队列和 SLA/业务流程的做法可参考 [Microsoft Dynamics 365 案件管理概览](https://learn.microsoft.com/en-gb/dynamics365/customer-service/administer/overview-cases)。

建议数据关系固定为：

`Person（唯一身份） → Customer/CompanyStaff/FamilyMember 关系 → Case（一次服务） → Checklist/Document/Timeline/Task/Deadline/Accounting`

具体做法：

- 客户主档只维护身份和联系方式；家族成员、公司职员只维护关系属性，避免复制姓名、生日、证件等身份字段。
- 受付只输入一次最少必要信息。若命中候选客户，默认复用主档；若未命中，才创建新档。
- 案件创建时根据“案件类型 + 申請区分”自动套用模板、担当规则和必填项。
- 页面始终显示一个“下一动作”，包括负责人、期限、阻塞原因和完成按钮；避免让用户在案件、提醒、任务三个页面来回寻找工作。
- 文档以案件为归属，上传后自动标记对应清单项；客户门户作为后续阶段，先把内部文件收集流程做完整。
- 会计记录默认带入客户、公司、案件上下文，可手动覆盖；报表从关联关系生成，而不是靠自由文本再筛选。

## 7. 受付与客户管理的输入减负方案

### 受付页改为三步

1. **识别对象**：姓名/姓名读音 + 生日作为基础，电话、邮箱、在留卡号/护照号作为辅助匹配；显示候选卡片及“这是同一人 / 新建客户”。
2. **选择服务**：案件类型、申请区分、公司关系、担当者。根据选择只显示该业务需要的字段。
3. **确认并开始**：一次确认将创建/复用客户、建立案件、套用清单、生成第一项下一动作；展示“本次新增了什么”，减少误建。

对于日期，使用独立的年/月/日输入、数字键盘和明确示例；对于错误，提交时展示页面顶部错误摘要，并链接回对应字段。该交互可参考 [GOV.UK 日期输入组件](https://design-system.service.gov.uk/components/date-input/) 和 [错误摘要组件](https://design-system.service.gov.uk/components/error-summary/)。

### 资料与字段规则

- 将字段分成“启动案件必填”“进入某状态时必填”“可后补”“不适用”。
- 对同一客户的联系方式、地址、证件有效期只存一次；案件只保存业务发生时的必要快照。
- 邮编、地址、电话格式、日期输入做标准化和自动校验；已有数据可一键带入，不要求重新输入。
- 家族成员的姓名/生日/证件字段不再复制维护；2 条旧式未关联记录应在业务确认后迁移。
- 缺失资料显示成待办，例如“护照期限：未确认”，而不是笼统的空白。

复杂服务可以使用带状态的任务清单，并支持稍后回来继续；[GOV.UK Task list](https://design-system.service.gov.uk/components/task-list/) 的模式适合本项目的案件清单，但应先简化流程，再把任务拆开。

### 第 0 阶段：恢复可交付性（1 周）

- 修复 4 个红色测试，并明确 Excel、PDF、期间余额的产品契约。
- 统一日本时区，补日期边界测试。
- 修复仪表盘服务端汇总/分页问题。
- 修复通用更新对 `registration_status` 的绕过。
- 补一条“受付 → 客户/案件/清单/时间线”集成测试。

验收：CI 全绿；97 客户、15 案件等规模下，仪表盘统计与数据库一致；跨日测试稳定。

### 第 1 阶段：客户主档与受付闭环（2 周）

- 引入客户候选匹配、复用/新建确认、重复合并工作台。
- 统一远程搜索选择器，覆盖客户、公司、担当者。
- 将受付、客户详情、案件详情共享同一套 Person/Customer 编辑组件。
- 迁移 2 条旧式家族记录；对 39 条联系方式空白数据提供批量补录清单。

验收：重复受付不会静默创建重复人；一次输入的信息在案件和公司关系中可复用。

### 第 2 阶段：案件作业台（2–3 周）

- 将下一动作、阻塞原因、负责人、期限、清单、文件放进案件主页面。
- 期限提醒改为“待处理 / 已完成 / 暂不提醒至某日”，必须支持原因和恢复。
- 统一案件状态机、登记状态机和时间线审计。
- 清单模板套用做幂等，支持追加缺失项而不重复。

验收：工作人员只需在案件作业台完成当天工作，不必在多个模块之间重复查找。

### 第 3 阶段：资料与会计关联（2–3 周）

- 案件文件上传、下载、版本、可见性和清单项联动。
- 支出/收入默认关联客户、公司、案件；客户/案件详情显示账务摘要。
- 完善 PDF/Excel 的稳定回归样例。

验收：从案件能追到文件和账务，从账务能回到案件；不会依赖自由文本搜索。

### 第 4 阶段：门户与自动化（之后）

- 内部流程稳定后再做客户门户、在线资料收集、通知、电子签名、日历同步。
- 门户只开放明确的案件文件和状态，采用对象级权限；不要直接复用内部列表 API。

## 9. 建议马上建立的测试矩阵

- 数据：重复客户候选、同名不同人、家族双向关系、旧式未关联记录。
- 日期：日本时间月末、23:59/00:00、闰年、期限已过/今天/未来。
- 权限：普通职员、主管、根账号、客户门户用户对客户/案件/文件的可见范围。
- 工作流：非法状态跳转、强制跳转理由、回退、撤回、完了后重新开启。
- 分页：20、21、100、500 条记录时的列表、下拉框、仪表盘汇总。
- 幂等：重复提交受付、重复套用模板、重复生成提醒、重复上传同一文件。
- 导出：无数据、单条、多税率、筛选条件、时区和文件名。
- 内容：日文术语一致、错误信息可理解、必填/条件必填/不适用清楚。
