## 文档目的（实施前的原文）

这是问题定位与修复设计（撰写时尚未实施；现已实施，见上）。本文件不授权推送、部署、生产迁移或生产数据写入。

用户目标：

1. 不动产列表支持完整搜索，并可对选中记录或当前筛选结果批量替换；例如月末将状况一键改为完了，或替换担当者、取引日。
2. 支出根据地点等文字联想类别；例如停车场、駐車場建议停车费。确认使用的类别应成为以后可选的支出类别。
3. 新规受付移除既存顾客照合、照合结果、新规登陆这套强制流程，只保留直接的业务信息输入；修复新顾客输入时的 400。

## 已定位的问题（实施前的状态，现已修复）

### 1. 不动产：只有单条变更，没有批量变更能力

- 列表已经有担当、段階、管理会社、支払状态、交易类型、归档状态、关键词和要补充的服务端筛选，见 frontend/src/pages/real-estate/RealEstateListPage.vue 与 backend/apps/real_estate/views.py。
- 列表没有多选框、全选当前筛选结果、批量编辑对话框或快速完了操作。
- API 只提供单记录 PATCH /api/real-estate/transactions/{id}/；RealEstateTransactionViewSet 没有 bulk action。前端循环发送 PATCH 会产生部分成功、权限/并发结果不一致、不可读批量履历等问题，不能这样实现。
- 现有 change_real_estate 是单条编辑权限。批量更改是高影响动作，当前没有独立权限、数量确认、选择快照或批量审计。

### 2. 支出：已有类别建议，但没有地点到类别规则，也不会沉淀类别主档

- backend/apps/accounting/category_suggestions.py 只做现有主档/本人历史的类别搜索、类别文字同义词建议，以及根据本人历史中完全相同地点推荐类别。
- 同义词词典中没有停车场 / 駐車場 → 停车费；而且它按用户输入的类别查询，不会按地点推断类别。
- 支出保存只写入 Expense.category 的自由文本。新输入的类别不会自动创建为 ExpenseCategory 主档；下次虽可能从本人历史中找到，却不会作为共享支出カテゴリ沉淀。
- 当前本人历史范围是正确的隐私边界，不能为了联想把其他人的支出内容暴露出来。

### 3. 新规受付：400 有两个明确根因，前端又隐藏了具体原因

当前 ReceptionNewPage.vue 强制先填写姓名和出生日期、点击既存顧客を照合、选择既有顾客或点击新規登録，才能进入业务信息。新規登録按钮只在照合完成后出现，因此这套流程本身就是用户所说的多余阻塞。

仅凭浏览器控制台的一行 POST 400 无法判定某次请求的唯一字段，仍应在 Network 面板读取响应 JSON。不过代码已确认两个确定的 400 路径：

1. 登录账号没有关联 Employee，且案件担当留空。ReceptionCreateView._resolve_case_responsible() 调用 CaseRule.resolve_create_responsible_id()；该规则在没有 policy.employee 时返回 responsible_employee：担当者を選択してください。这不是客户姓名输入错误。
2. 创建新顾客时未提供出生日期。ReceptionCustomerSerializer.birth_date 是必填；家族的新建数据也要求出生日期。当前页面虽然第一步要求出生日期，但流程切换和新规按钮的可用性让校验不透明。

另一个 UX 问题是 submitReception() 把任意 400 都显示为“新規受付の登録に失敗しました。入力内容をご確認ください。”，没有显示字段名和后端错误文本，因此用户无法知道是担当、出生日期、案件种别还是申请区分失败。

## 推荐修复方案（已按此实施，差异见文首）

### A. 不动产搜索与批量替换

#### 交互

保留现有服务端筛选，并增加：

- 搜索区增加 取引日（开始/结束）、振込状态；关键词继续覆盖编号、当事者、物件、房间号、备注；不按 Employee、用户账号或担当 ID 搜索。
- 表格第一列为多选框，并提供选择本页、选择当前筛选的全部 N 件、清除选择。全部必须由服务端根据当前筛选重新计算，不能由前端仅用当前页 ID 假装全选。
- 工具栏提供批量修改；字段仅限段階（状况）、担当者（自由文本）、取引日。显示“只改已勾选字段，其他字段保持不变”。
- 对段階 → 完了提供快捷按钮。点击后仍显示将影响的记录数、过滤条件摘要与最终确认；这是确认后的单次提交，不是静默批量写入。
- 默认只操作利用中的记录；归档记录不能混入。恢复/归档继续使用已有专用 action，而不是让批量编辑改 is_archived。

#### API、一致性与履历

新增专用 action：POST /api/real-estate/transactions/bulk-update/。不要让前端循环调用单条 PATCH。

请求结构：

    {
      "selection": { "mode": "ids", "ids": [101, 102] },
      "changes": {
        "stage": "settled",
        "responsible_name": "田中",
        "transaction_date": "2026-10-31"
      },
      "expected_count": 2
    }

对于当前筛选全部，selection 改为服务端允许的筛选参数和由预览端点签发的短期 selection_token；token 固化匹配 ID、操作者、筛选摘要、数量和过期时间。提交时服务端复核 token、权限、记录仍为利用中、expected_count，不接受浏览器声称的任意 ID 或数量。

- 只允许上述三个字段；空 changes、未知字段、空担当是否代表清空必须明确约定。推荐以 null 或 clear_fields 显式表示清空，避免空字符串误删。
- 使用事务。先验证全部目标都在当前用户的授权查询集内；任何一条不可编辑、归档、token 失效或数量改变则整批 409/400，不做部分写入。
- 每条记录复用 transaction serializer 的字段校验；批量 action 不得绕过归档限制、金额校验、业务权限和更新时间/操作者设置。
- 不直接改法定台账或已锁定台账。交易记录变更与台账更正是不同业务动作；如果某字段将来会同步到台账，应显式提示“需要台账更正”，不能静默覆盖锁定台账。
- 每条记录写一条现有不动产业务履历，格式保持时间 / 操作者 / 做了什么 / 实际变更前后值；另写一条汇总审计（批次数、筛选摘要、变更字段），普通页面不显示字段 ID、JSON 或权限名。

#### 权限、测试与验收

新增显式业务权限 real_estate.bulk_change_real_estate，并加入模型 Meta.permissions、迁移、BUSINESS_PERMISSION_CODES 与角色同步。

- 推荐默认：李的 system_admin 明确拥有该权限；普通不动产授权用户继续拥有单条查看/新建/编辑协同权限，但不自动取得批量写权限。若事务所确认某些普通用户需要月末批量作业，再显式授予。不要使用 is_superuser，不要扩散到会计、案件、顾客或文件模块。
- 李：按筛选全选、批量完了、批量担当自由文本、批量取引日；逐条履历均显示真实操作者和实际前后值。
- 拥有 change_real_estate 但无 bulk 权限的普通用户：单条编辑正常，批量端点 403；有显式 bulk 权限的普通用户：可批量改他人担当记录，不因担当文字或 Employee 关联被拒绝。
- 错误场景：空改动、未知字段、重复 ID、归档记录、过期/篡改 token、数量变化、未授权 ID 都不会产生部分修改。

### B. 支出类别自动联想与沉淀

保持 Expense.category 可自由手输；自动联想只能建议或在用户确认后应用，不能静默把用户输入改成别的会计类别。

新增可维护的地点/文本到类别规则（建议模型名 ExpenseCategorySuggestionRule）：

- pattern：标准化后匹配的文字，例如 駐車場、停车场；match_field：place、expense_target 或 note。
- expense_category：FK 到 ExpenseCategory；再带 priority、is_active、source、created_by/updated_by、时间戳。
- 匹配使用现有 NFKC、大小写与空白归一化；规则只能给出候选类别，不上传外部 AI，也不读取他人的支出明细。
- 初始迁移/数据迁移以可审核的规则建立 駐車場 / 停车场 / parking → 停车费。名称统一由事务所确认后确定，不能同时产生停车费和駐車場代等重复主档。

保存一笔支出时：

1. 用户手输或确认一个非空类别后，以规范化名称 get_or_create 活跃 ExpenseCategory（并处理唯一性并发）。这样该类别成为下一次 autocomplete 的主档候选。
2. 首次由用户确认地点 A → 类别 B 时，提供记住这个对应关系复选项，写入规则；不要从单笔记录自动把每个地点都提升为全局规则。
3. 类别主档的新增、规则新增/编辑应有明确管理权限。若普通录入即创建类别是业务要求，保存服务可受控创建类别，但规则维护/删除仍需 manage_expense_category；实现前在测试中锁定边界。

扩展现有 /api/accounting/expenses/category-suggestions/ 响应，增加 place_recommendations，含类别、命中规则说明、是否需要确认；原有 matches、normalized、个人历史推荐继续保留。在 ExpenseFormFields.vue 中，输入地点后显示“建议类别：停车费（地点：駐車場）”和采用按钮；用户点选后填充 category。手输类别永远可保存。

测试：两种停车写法均建议统一类别；未确认时不修改表单/数据库；确认后类别写入；手输新类别后创建或复用一个主档；个人历史不泄漏他人数据；规则禁用后不建议；规则管理需要明确权限。

### C. 新规受付：只保留直接业务信息输入

将 /reception/new 从客户识别 → 业务信息 → 确认的强制照合流改为业务信息输入 → 确认并创建。移除以下前端 UI 和状态：

- matchCustomers 调用、identifyForm、matching、matchDone、候选人列表、customerDecision、selectedCandidate；
- 既存顧客を照合、照合結果、この顧客を使用、新規登録按钮与必须先做出对照选择的守门逻辑。

新页面直接显示：新顾客基本信息（姓名、出生日期为必填）、案件种别、申请区分、案件担当、受任日，以及现有的可选公司和家族信息。确认页只显示直接输入的业务摘要。

为避免破坏其他 API 调用方，后端可暂时保留 existing_customer_id/existing_company_id 的兼容支持；但该页面不再发送 existing_customer_id，不再执行客户照合。后续若确认没有其他客户端使用，另开任务删除旧 API 分支和相关测试，不能在本次 UI 简化中猜测删除。

#### 修复 400 与错误呈现

- ReceptionCreateView 不应把未关联 Employee 的用户变成无法创建新规受付的无解释 400。推荐方案是：页面的案件担当为必填的有效 Employee；若当前用户无 Employee 关联，不显示留空自动设为本人的误导文案，并在提交前提示选择。若业务确认允许未分配案件，必须单独改 Case 的创建、可见范围与后续分配规则，不能只把后端限制删掉，否则创建者可能看不到自己刚创建的案件。
- 若目标是任何有 case create 权限的账号可直接登记且暂不指定担当，应将 Case 的 responsible_employee 置空作为明确定义，并新增基于创建者的可见/待分配规则及测试；这是权限模型变更，需要单独确认，不能暗改。
- ReceptionCustomerSerializer 继续把新顾客姓名与出生日期作为明确必填；前端在提交前显示字段错误。
- 前端 catch 必须解析 DRF 响应字典并在表单项下或错误摘要中显示真实字段错误；409 仍显示幂等处理中；不再把所有 400 伪装成笼统失败。
- 新增 API 测试覆盖未关联 Employee + 未选担当的结构化 400，以及页面测试/浏览器验收确认错误能显示担当者字段而不是泛化消息。

#### 验收

- 新规受付页面不出现照合、照合結果、新規登録（照合结果内）按钮；用户无需先运行客户匹配即可填写业务信息。
- 用新顾客数据（姓名+出生日期）创建案件成功；没有 Employee 的账号若漏选案件担当，看到可读、字段级的错误；选择有效担当后成功。
- 400 响应体在浏览器 Network 和页面错误摘要一致；同一个 request_id 的成功重试仍不重复创建。
- 现有客户匹配 API 如被保留，其独立测试继续通过；不在本次把它扩散或用于新规受付。

## 实施前的业务确认点（已确认：批量权限只给李）

推荐默认是“批量修改需要独立权限，普通协同用户保持单条编辑”。如果希望所有拥有 change_real_estate 的普通用户也可月末批量修改，应在实施前明确确认；这会扩大高影响写权限，但仍只限不动产模块。
