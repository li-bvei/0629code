# SUNRISE 业务扩展与权限开发要求

更新时间：2026-09-27  
状态：需求已确认，尚未实施  
适用项目：SUNRISE 日本行政书士事务所内部业务管理系统

> 本文件记录 2026-09-26 确认的完整开发要求，是后续方案设计、任务拆分和验收的业务基准。  
> `docs/AI_HANDOFF.md` 仍是 AI 的第一阅读入口；代码、migration 和测试是“当前已经实现什么”的最终依据。  
> 本文件不是已完成功能清单，也不是法律意见。涉及法定保存期限、电子交付和个人信息处理时，上线前必须再次核对届时有效的日本法令及事务所实际业务。

## 1. 总体原则

1. 尽可能保持现有项目大结构、路由习惯和领域模型，不为本次需求进行全项目重写。
2. 各业务模块必须独立保留，不能为了统一管理而合并成一个大模块、大页面或大数据表。
3. `Case` 继续作为行政书士案件主线；其他模块可以通过外键、只读摘要和跳转相互关联，但不得互相吞并。
4. 会计、案件、材料/文件、Visa 帐票、不动产、账号权限分别维护自己的业务状态、权限和页面职责。
5. 优先扩展现有能力：Checklist 使用现有 Case Checklist，文件使用现有 Document，会计与 Visa 保留现有入口。只有确属新业务领域的不动产模块新增独立 app。
6. 普通用户默认只能处理自己的业务数据。用户 A 不得查看或修改用户 B 的个人业务记录；跨用户查看、修改必须由管理员明确授权。
7. 前端隐藏按钮不等于权限控制。列表、详情、写入、导出、文件下载和批量操作都必须由后端执行权限及数据范围校验。
8. 所有重要操作必须可追踪。业务进展写入 Timeline，系统访问和修改写入独立 AuditLog，二者不能混为一张表。
9. 涉及历史数据迁移、批量删除、金额重算、文件移动或权限重置，必须先备份、预览影响范围并取得用户确认。
10. 每个开发批次必须同步更新 AI 交接文档、开发计划、必要的数据模型说明、测试结果和回滚说明；没有更新交接文档不得视为完成。

## 2. 模块边界

| 模块 | 保留方式 | 主要职责 | 允许的跨模块关系 |
|---|---|---|---|
| 案件 Case | 保留现有 `cases` | 案件状态、负责人、期限、Checklist、Timeline | 显示材料、帐票、会计、不动产的摘要和链接 |
| 顾客/公司 | 保留现有 `customers` / `companies` | 人物和法人主档、关系复用 | 被案件、会计、不动产等引用 |
| 材料/文件 | 扩展现有 Checklist + Document | 必要材料、收件、审核、上传、下载、替换和归档（第一阶段不做完整版本管理） | 关联 Case；不吸收报价或会计明细，不连接 Google Drive |
| 会计 | 保留现有 `accounting` | 支出、收入、项目损益、个人报销、税务相关功能 | 可选关联 Customer、Company、Case |
| Visa 帐票 | 暂保留现有 `accounting/vouchers` 位置 | CSV/XLSX 导入、校验、批量生成 PDF | 可选关联 Customer、Case |
| 报价/契约/请求/领收 | 作为独立帐票能力逐步完善 | 各自的编号、状态、金额和 PDF | 通过 Case/Customer/Company 相互查看，不共用一套状态 |
| 不动产 | 新增独立 `real_estate` 领域 | 租赁/买卖记录、宅建业法台账、佣金和内部结算 | 引用主档、Document、Accounting，不并入 Case |
| 账号与权限 | 扩展现有认证/员工体系 | 模块权限、数据范围、所有权、委派和审计 | 对所有业务模块统一实施访问控制 |

“统一管理”是统一入口、统一检索、统一关联和统一权限规则，不是把所有业务数据合并到同一个模块。

## 3. 现有案件业务与残留代码整理

### 3.1 保留内容

- 保留现有 13 个 Case 状态及专用状态变更逻辑，未经用户确认不得删减或重排。
- 保留新规受付、Customer/Company 复用、Checklist、Timeline、Document、Task、Reminder 和 Portal 的既有后端方向。
- 保留已经完成的顾客、公司和案件记录工作台，不因本次扩展重新设计整个页面体系。
- 不在本次需求中拆分 Person/Customer；以后如需建立统一人物主档，必须先单独确认模型和迁移方案。

### 3.2 清理规则

- 参考成熟开源项目时重点学习领域边界、审批流、导入预览、文档索引、权限和审计方式，不直接复制不适合本项目的复杂 ERP 结构。这里的“文档索引”仅指本系统内部 Document 的文件元数据（分类、关联、哈希等），不是 Google Drive 索引；Drive 本阶段不连接、不索引。
- 可参考 Odoo、ERPNext、Paperless-ngx、django-import-export 等项目的成熟模式；采用代码前必须核对许可证、版本、依赖和本项目适配性。
- 先列出候选清单，再通过路由、import、API、数据库数据、测试和 Git 历史确认是否仍被使用。
- 可优先检查：已注释旧实现、明确的调试脚本、重复备份映射文件、无入口占位页、失效的临时 HTML。
- 不得删除 migration、生产数据相关逻辑、Task/Reminder/Document/Portal 整个模块，或仅因前端暂时隐藏就判断后端无用。
- 实际删除前必须提供“删除对象、引用检查、数据影响、恢复办法”，并由用户确认。

## 4. 材料清单与文件管理

### 4.1 功能位置

- 第一阶段不新建独立 `materials` app，优先扩展现有 `CaseChecklistTemplate`、`CaseChecklistTemplateItem`、`CaseChecklistItem` 和 `Document`。
- 案件详情显示材料摘要和快捷入口；完整材料维护仍在 Checklist/Document 的职责范围内。
- 不同业务种类使用可版本化模板，创建案件时复制为案件快照，避免以后修改模板影响历史案件。

### 4.2 材料项目字段

- 材料名称、材料类型、说明、是否必需、责任方、负责人。
- 状态：未开始、已请求、已收到、审核中、已确认、需补正、免除、不适用。
- 请求日、预计取得日、收到日、审核日、有效期限。
- 关联文件、审核人、备注、补正理由、模板版本。
- 所有状态变更记录操作者、时间和来源，并生成必要的业务 Timeline。

### 4.3 公司解散模板示例

模板应允许配置公司登記簿謄本（履歴事項全部証明書）、盖章委任状、现有公司账目、决算报告、定款、股东/董事资料、印鉴证明、解散日、清算人资料等。这里是可编辑模板示例，不应硬编码为所有案件通用必填项。

### 4.4 现有系统文件管理

2026-09-27 已确认：本阶段不迁移 Google Drive 文件，也不建设 Drive 索引、同步、OAuth 或混合存储。现有 Google Drive 内容保持原状，与本次开发无关。

本阶段只完善系统已有的 Document 文件管理：

- 支持在系统内上传、下载、分类、关联 Case/Checklist 和归档。
- 文件必须通过后端鉴权访问，不能依赖可猜测的公开静态 URL。2026-09-27 发现生产 nginx 直接公开 `/media/`、`/sun/media/`，已提升为 P0 安全项（见 `DEVELOPMENT_PLAN.md` P0-A8）。
- 保存原始文件名、存储名、MIME、大小、哈希、上传人、上传时间、关联对象和归档状态。
- 权限继承关联 Case（按担当 Employee 的 `assigned` 范围）；未关联 Case 的文件由上传人或明确授权范围控制。
- **第一阶段不建设完整版本管理**：不做版本树、版本比较和版本恢复；替换文件只需写入 AuditLog。完整版本管理以后再评估。
- 上传时检查文件类型、大小和恶意文件；文件名不得作为唯一标识。
- 普通用户只访问本人所有或被指派案件的文件；跨用户查看、下载和导出按权限范围控制。
- 敏感文件的查看、下载、替换、归档和删除写入 AuditLog。
- 制定系统文件目录、备份、恢复、保留和删除规则；批量删除前必须预览并确认。
- My Number 继续按现有方式在系统数据库中加密保存，不因文件管理功能改变其存储方式。

## 5. 会计模块

### 5.1 保留范围

- 会计模块整体必须独立保留，不并入案件或其他模块。
- 保留现有会计首页、支出、分类、收入、车辆使用、会计项目、项目损益、Excel 导出、税务计算和现有帐票能力。
- 用户曾提出“不常用精算部分”，只表示可评估简化或隐藏某些操作，不代表删除整个会计模块。现有 `is_reimbursed` 等字段保持现状，不扩展为审批状态机，也不得在未核对用途前直接删除。

### 5.2 支出分类输入

支出单独追加时，分类输入调整为：

1. 可搜索现有分类；
2. 找不到时允许手动输入并按权限创建新分类；
3. 根据当前用户自己的历史记录，结合支付地点、用途、备注、最近使用和使用频率推荐分类；
4. 建立同义词和规范名称，避免“交通费/交通费用”等重复分类；
5. 推荐只作为候选，保存前必须由用户确认；
6. 默认不读取其他普通用户的报销内容训练或推荐，避免数据泄露。

第一阶段优先使用本地规则和历史匹配，不依赖外部生成式 AI。

2026-09-27 确认：第一阶段继续保留 `Expense.category` 自由文本，不强制改为 `ExpenseCategory` 外键，也不批量清洗旧数据。规范分类只作为建议，必须保留用户原始输入，不得自动批量重写历史 Expense。

### 5.3 个人报销与数据隔离

- 每条支出/报销必须有明确所有者 `owner`，并记录创建人和最后修改人。
- 2026-09-27 已确认：现有 Expense 全部属于当前用户本人的报销数据。历史归属 dry-run 应全部映射到该账号，正式回填前仍需核对记录数量和目标账号，防止技术性误写。
- 普通用户只能新建、查看和修改自己的报销记录，不能查看或修改其他人的记录。
- 报销保持现有的简单登记方式，不新增提交、审核、批准、支付、入账或退回流程，也不新增相应状态机。
- 现有 `is_reimbursed` 等字段保持现状；除非以后用户提出新要求，不据此扩展审批流程。
- 2026-09-29 用户决定：「精算済み」前端显示全部废止；`is_reimbursed` 作为历史兼容字段保留在模型、数据库和 API 中，不删除、不迁移、不修改历史数据，不构成报销流程。
- 经授权的会计管理员可以按人员、期间、分类、状态和项目筛选全部记录。
- “查看全部”“修改全部”“导出全部”必须是不同权限；默认跨用户查看应为只读。
- 系统管理员不应仅因为能管理账号就自动获得全部会计数据查看权。

## 6. Visa 返签表批量作成

### 6.1 结构原则

- 暂时保留当前 `accounting/vouchers` 中的 Visa 功能位置，不为移动目录而移动目录。
- 现有“选择客户 + 粘贴 TSV”的方式可保留为辅助入口，主流程改为 CSV/XLSX 文件导入。

### 6.2 目标流程

```text
下载标准模板 → 上传 CSV/XLSX → 选择工作表 → 自动识别列
→ 必要时手动映射 → 数据预览与逐行校验 → 用户确认
→ 批量创建生成任务 → PDF 生成 → ZIP 下载 + 错误报告
```

### 6.3 必须处理的边界

- 支持 CSV 常见编码、XLSX 多工作表、日期格式、前导零和空白行。
- 显示原始值、转换值和错误原因；存在错误时不得静默跳过。
- 支持共享字段与逐行字段、模板版本、重复导入检测和幂等 request ID。
- 允许“全部成功后提交”或“有效行生成、错误行报告”两种模式，但默认策略必须明确。
- 输出 ZIP、成功/失败数量、逐行错误 CSV；失败任务可重试且不能重复生成成功记录。
- 敏感字段不得完整写入普通应用日志；下载和批量导出必须审计。
- 可选关联 Customer、Case，但不强制把导入内容写进 Customer 主档。

## 7. 报价、契约、请求和领收帐票

- 报价书、契约书、请求书、领收书分别保留独立业务状态、编号规则、金额快照和 PDF 模板。
- 可以统一放在“帐票/契约管理”导航区域，并从 Case、Customer、Company 查看关联摘要。
- 不把四种文书合并成一个只有 `type` 的万能流程；共用的仅限编号、金额计算、PDF、版本和审计基础能力。
- 案件材料清单可以要求“契约书已签署”“请求书已发送”等确认项，但材料状态不能代替帐票状态。
- 现有 `/vouchers/*` 方向保留；尚未实现的占位功能可暂时隐藏，不应直接删除未来能力。

## 8. 不动产租赁/交易记录模块

### 8.1 模块定位

- 新增独立 `real_estate` app、API 和前端导航，不并入 Case 或 Accounting。
- 第一阶段以租赁为主，同时保留交易类型字段，因为现有 Excel 中存在至少一条买卖记录。
- 使用“列表总览 + 单笔记录工作台”结构。列表便于查看全体状态、负责人、款项和缺失项；详情显示当事人、物件、法定台账、文件、金额、付款和变更历史。

### 8.2 新规输入

首次创建仅要求：客户/当事人名称、物件、房间号、管理公司、负责人、交易类型（默认租赁）和当前阶段。其余法定字段按业务阶段逐步补充，不在第一屏一次性要求全部输入。

可从既有 Customer/Company 搜索复用，也允许先录入轻量当事人；但后续匹配主档时必须预览，不自动合并。

### 8.3 数据结构方向

- RealEstateTransaction：编号、类型、阶段、担当者自由文本、重要日期、备注、归档状态。担当者不关联账号、Employee 或权限。
- Property/Unit：所在地、名称、房间、种类、面积等物件信息。
- TransactionParty：出租人、承租人、卖方、买方、代理/媒介相关当事人。
- BrokerageCompany/Manager：管理公司和共同参与的宅建业者。
- LegalLedger：法定台账字段、年度关闭、保存期限、锁定和更正版本。
- FinancialSummary：租金/价格、佣金、广告费、振込、手续费和内部结算摘要。
- InternalProfitDistribution：与交易关联的内部利润分配，记录分配对象、计算方式、比例/固定金额、分配金额、备注和结算状态；仅限明确授权人员查看，不属于法定宅建台账。
- DocumentLink：媒介契约、重要事项说明、契约书、本人确认和其他证明文件。
- AccountingReference：在会计模块中的收支引用，不复制会计分录。

### 8.4 宅建业法相关保存设计

根据目前查到的国土交通省规则，台账至少应覆盖：交易类型/代理/媒介、各方及代理人姓名地址、共同宅建业者、土地建筑概要、价款或租金、报酬、特约、交易日期、所在地和面积等。电子保存必须能够在事务所明确显示和打印。

保存期限按会计年度关闭管理：通常至少 5 年；宅建业者自行出售的新建住宅记录通常为 10 年。系统不得到期自动物理删除，先进入“到期复核”，并支持 legal hold、延长保存和销毁审批。

上线前以届时有效的官方资料复核：

- 国土交通省施行规则参考：<https://www.mlit.go.jp/common/001180493.pdf>
- 国土交通省电子化说明：<https://www.mlit.go.jp/totikensangyo/const/sosei_const_tk3_000092.html>
- 北陆地方整备局宅建业者义务说明：<https://www.hrr.mlit.go.jp/kensei/sangyo/fudousan/duty.html>

## 9. 账号、权限和多人同时使用

### 9.1 账号关系

- 扩展现有认证和 Employee，不创建第二套登录体系。
- 建立 `User` 与 `Employee` 的明确一对一关系；历史账号先列出映射清单再迁移。
- 这是事务所内部多用户系统，不是多租户 SaaS；无需为每位员工建立独立数据库。

### 9.2 权限模型

采用“模块动作权限 + 数据范围”的最小可扩展模型：

- 模块动作：查看、新建、修改、删除/归档、导出、管理设置；仅对确实存在审批业务的其他模块再单独增加审批权限，个人报销不使用审批权限。
- 数据范围：`own`（本人所有）、`assigned`（本人被指派）、`all`（全部）；以后确认有需要再增加部门范围。
- 管理员可以为每个用户或角色分配可见模块、可执行动作和数据范围。
- 普通用户默认 `own`/`assigned`，不得通过修改 URL、API 参数或导出接口访问他人数据。
- 不动产是协同台账例外：具备不动产入口及相应动作权限的普通用户可查看、新建、编辑全部不动产记录；担当文字不产生数据范围或权限。

### 9.4 并发与锁定

- 普通情况下 A 不能修改 B 的内容，后端必须执行对象所有权检查。
- 同一用户多窗口、管理员代办或多人同时编辑获授权的共享记录时，使用版本号/更新时间进行乐观锁；冲突时提示刷新并比较变化，不能后写静默覆盖前写。
- 已完成案件或法定台账已关闭的记录默认锁定；更正需专用动作、理由和权限。个人报销保持现有简单登记，不增加审批锁定状态。
